# ERC-4337 (2021) — Account Abstraction Using Alt Mempool

**Citation:** Buterin, V., Weiss, Y., Tirosh, D., Nacson, S., Forshtat, A., Gazso, K., & Hess, T.
2021. "ERC-4337: Account Abstraction Using Alt Mempool." *Ethereum Improvement Proposals*, no.
4337 (Final, created 2021-09-29). https://eips.ethereum.org/EIPS/eip-4337.
**Analytical level:** Structural + Parametric
**Most relevant design decisions:** Q3, Q4, Q5, Q7

---

## Q3 — Mandate Selection

Rationale, "Paymasters" section: a Paymaster is a helper contract that pays transaction fees on
behalf of a sender, using a "pre-charge, and later refund" model. This is the mechanism behind
the "Account Abstraction" named pattern already referenced in `institutionalDesign.md` §2 (Powers
+ ERC-4337 paymaster for gasless governance). The actionable design choice it exposes: gas
sponsorship should be modeled as its own mandate with its own accountability surface (see Q7), not
folded silently into whichever execution mandate it subsidizes — a paymaster that goes wrong (or
is drained) is a distinct failure mode from the governance action it was sponsoring.

Rationale, "The main challenge..." section: the proposal's central structural move is a clean
separation between *validation* (does this operation deserve to run and who pays) and *execution*
(actually running it) — "only after validation is successful and the UserOperation can pay, the
execution is done, and only done once." This two-phase separation is the same underlying pattern
as Powers' `needFulfilled` chain from a proposal/vote mandate into an execution mandate: gate
execution on a cheap, revertible validation step so that expensive or irreversible execution never
runs against an invalid or unauthorized request. Use it as independent confirmation of the
Optimistic Execution and Bicameralism patterns already documented — validate-then-execute is a
general two-phase design, not specific to voting.

## Q4 — Dependency Chains

"Semi-abstracted Nonce Support" section: rather than a single sequential nonce, ERC-4337 splits
the nonce into a 192-bit "key" and a 64-bit "sequence," so a sender can maintain multiple
independent, parallel ordering streams — the worked example is "an 'administrative' channel of
operations running in parallel to normal operations," gated on a distinct key so admin actions are
never blocked behind a backlog of normal-flow operations. This is a directly reusable pattern for
Powers flow design: an emergency/administrative mandate chain (e.g. the flow position(s) targeted
by `PauseMandates`) should be structured so it does not share a `needFulfilled` dependency with
the normal-operations flow it needs to interrupt — otherwise a stalled normal flow can block the
very emergency mechanism meant to unstick it. Treat "does this emergency mandate have an
independent path to execution, or does it inherit a dependency on the flow it's meant to
override?" as a design check whenever adding a `PauseMandates` instance.

## Q5 — Membership Design

Rationale, "Reputation Rationale" section: privileged infrastructure roles (paymasters, factories)
are required to stake in order to gain relaxed operating privileges, but the stake is explicitly
"never slashed" — "the only use for the stake [is] in sybil attack prevention." This is a
distinct pattern from the more common bonded-collateral-with-slashing model: here, the stake's
entire function is to make Sybil attacks (spinning up many low-cost fake entities to abuse
shared infrastructure) economically irrational, not to fund compensation for a specific harm.
When a Powers design considers a staking requirement for role entry, separate these two purposes
explicitly: a stake meant to deter Sybil/spam entry only needs to be costly to acquire (no
slashing mechanism required), while a stake meant to secure against in-role misbehavior needs an
actual slashing mandate tied to the accountability chain. Conflating the two leads to either an
unnecessarily complex slashing mechanism for a pure-entry-cost problem, or an ineffective
pure-cost stake where actual misbehavior protection was needed.

## Q7 — Accountability and Monitoring

"Error codes" section: every validation failure is attributed to a specific entity (sender,
factory, or paymaster) via call-tracing, and surfaced through a structured code (`AA1x` = sender
creation, `AA2x` = sender validation, `AA3x` = paymaster validation) rather than an undifferentiated
revert. The general principle — every failure path in a multi-party flow should be attributable to
the specific mandate/entity that caused it, not just to "the transaction failed" — is directly
applicable to `needFulfilled`/`needNotFulfilled` chains with several mandates in sequence: design
chains so that a failure at any step is unambiguous about which upstream mandate is responsible,
which matters when the chain includes an external party (a paymaster-equivalent sponsor, an
external validator) whose failure should not be indistinguishable from the requester's own
failure.

Rationale, "Reputation Rationale" section (continued): bundlers "throttle down (or completely ban
for a period of time) an entity that causes invalidation of a large number of ... operations,"
implementing a graduated, automatic, usage-triggered sanction rather than a governance-voted one.
This is a machine-enforced variant of the graduated-sanctions design principle (see
`ostrom_2005.md` Design Principle 5): for infrastructure-adjacent roles that interact with the
system at high frequency (bots, keepers, relayers), consider an automatic, non-discretionary
throttle (`RevokeInactiveAccounts`-style or a bespoke rate-based check) rather than requiring a
full `StatementOfIntent` vote for each instance of low-grade misbehavior — reserve voted
sanctions for cases serious enough to need human judgment.

## What to skip

The great majority of this document — the exact `UserOperation`/`PackedUserOperation` field
layouts, the `EntryPoint.handleOps()` verification/execution loop mechanics, gas accounting and
`preVerificationGas` estimation, the bundler mempool propagation and simulation rules, EIP-7702
delegation specifics, and storage-layout/transient-storage implementation warnings — is Ethereum
infrastructure engineering with no governance-design analogue. It answers "how do you build a
gasless-transaction relay layer," not "how should authority and accountability be structured,"
and should be treated as background for anyone implementing the `AccountAbstraction` pattern
rather than as source material for constitution design.

## Mandate implications

- Model gas-sponsorship (paymaster-equivalent) mandates as their own accountability surface,
  separate from the execution mandate they subsidize.
- Structure emergency/override mandate chains (`PauseMandates` targets) with an independent path
  to execution that does not share a `needFulfilled` dependency with the normal flow they are
  meant to interrupt.
- When requiring a stake for role entry, decide explicitly whether its purpose is Sybil/spam
  deterrence (no slashing needed) or misbehavior insurance (requires a slashing mandate tied to
  the accountability chain) — do not default to bundling both into one undifferentiated stake.
- In multi-step `needFulfilled` chains involving an external party, ensure failures are
  attributable to the specific responsible mandate/entity rather than collapsing into an
  undifferentiated failure.
- For high-frequency, low-stakes infrastructure-adjacent roles, prefer automatic graduated
  throttling over voted sanctions, reserving `StatementOfIntent`-gated accountability actions for
  cases that need human judgment.
