# ERC-8004 (2025) — Trustless Agents

**Citation:** De Rossi, M., Crapis, D., Ellis, J., & Reppel, E. 2025. "ERC-8004: Trustless
Agents." *Ethereum Improvement Proposals*, no. 8004 (Draft, created 2025-08-13).
https://eips.ethereum.org/EIPS/eip-8004.
**Analytical level:** Structural + Dynamic
**Most relevant design decisions:** Q1, Q3, Q4, Q5, Q7

---

## Q1 — Role Structure

Abstract: "Trust models are pluggable and tiered, with security proportional to value at risk,
from low-stake tasks like ordering pizza to high-stake tasks like medical diagnosis." This is the
core structural insight for any constitution that assigns roles to AI agents: the amount of
governance oversight a role requires should scale with the stakes of what the role can do, not be
uniform across all agent-held roles. Use it as a role-design heuristic distinct from Ostrom's
size-based heuristics (`institutionalDesign.md` §4 "Heuristics by organisation size"): scale
`votingPeriod`, `timelock`, and `needFulfilled` validation-gate requirements to the *value at
risk* of the specific mandate an agent role can trigger, not to the number of role-holders.

Identity Registry section: an agent's on-chain identity (`agentId`) is owned by an address that
can transfer ownership or delegate management to "operators" separately from the identity itself.
In Powers, an `allowedRole` check on an agent's address does not guarantee behavioral continuity —
the underlying model, weights, or operating logic behind that address can change without any
on-chain signal, unlike a human role-holder whose judgment changes slowly. Treat "the agent
address has held this role for N blocks without incident" as weaker evidence of trustworthiness
than the equivalent claim for a human-held role, and prefer mandates with bounded, auditable
`target`/`value` scope over broad `OpenAction` grants when the role-holder is agent-controlled.

## Q3 — Mandate Selection

Abstract & Security Considerations: three pluggable trust models are named — reputation
(aggregated client feedback), validation (stake-secured re-execution, zkML proofs, or TEE
attestation), and crypto-economic staking. Each is a different mandate-selection pattern for
gating agent-triggered actions:
- **Reputation-gated:** cheap, retrospective, tolerant of occasional bad outcomes. Maps to a
  `BespokeAction_Simple` execution mandate with no pre-execution gate, paired with a downstream
  accountability chain (see Q7) that can revoke the role after a pattern of poor feedback.
- **Validation-gated:** an independent check must pass *before* the action's effects are treated
  as final. Maps to `CheckExternalActionState`/`ExternalAction_Simple` chained with
  `needFulfilled` in front of the actual execution mandate — the agent's proposed action is
  recorded, an external validator contract checks it, and only a passing validation unlocks
  execution.
- **Crypto-economic/staked:** the agent posts a bond forfeited on detected misbehavior. Maps to
  pairing role assignment with a `SafeAllowance_Transfer`-style bonded deposit and a slashing
  mandate triggered by the same accountability chain used for revocation.

Choose the trust model per mandate based on cost of a false positive (an agent action wrongly
allowed to proceed) vs. cost of latency (an agent action delayed by validation): low-stakes,
reversible actions should default to reputation-gated with no `timelock`; high-stakes,
irreversible actions (treasury transfers, role assignment changes) should require
validation-gated or staked models regardless of an agent's accumulated reputation, since
reputation is a lagging indicator and does not prevent a single catastrophic action.

## Q4 — Dependency Chains

Validation Registry section: `validationResponse()` can be called multiple times for the same
request, enabling "progressive validation states (e.g., 'soft finality' and 'hard finality')."
This is a reusable pattern for `needFulfilled` chains gating agent-triggered mandates by
increasing certainty: a first (soft) validation response could unlock a low-risk preparatory
mandate (e.g., staging a transaction), while only a second (hard) validation response unlocks the
actual value-transferring mandate. Use progressive `needFulfilled` gates instead of a single
binary check whenever an agent-initiated action has both a cheap-to-reverse preparatory step and
an expensive-to-reverse final step.

Rationale section (gas sponsorship / EIP-7702): because feedback submitters don't need to be
pre-registered, "any application can implement frictionless feedback." This lowers the
`allowedRole` bar for who can trigger the *reporting* side of an accountability chain (feedback
recording) even while keeping the bar high for who can trigger the *consequential* side
(revocation/slashing) — a useful split when designing a two-stage `StatementOfIntent` (open
reporting) → `RevokeAccountsRoleId` (role-gated action on aggregated reports) chain for an
agent-held role.

## Q5 — Membership Design

Identity Registry / Registration section: registration is open (`SelfSelect`-equivalent — "New
agents can be minted by calling `register()`") but produces only a *discovery* identity, not
automatically a trust or governance grant: "If [`supportedTrust`] is absent or empty, this ERC is
used only for discovery, not for trust." This is an important boundary-rule distinction for
Powers designs: an open `SelfSelect`-style entry into a base "registered agent" role should be
kept separate from, and strictly weaker than, an `allowedRole` grant on any mandate with real
governance power — registration proves an agent *exists and is addressable*, not that it should
be *trusted*. Route agents through a second, higher gate (`PeerSelect`, staking, or a validation
history threshold) before granting any consequential `allowedRole`.

Security Considerations: "Sybil attacks are possible, inflating the reputation of fake agents."
Open agent registration combined with reputation-based trust is Sybil-vulnerable by default. If
a Powers constitution grants roles to agents based on accumulated on-chain reputation, pair the
open registration/reporting boundary rule with a Sybil-resistance mechanism on the *reporting*
side (e.g., `ERC721_GatedAccess` or `ZKPassport_Check` gating who can submit feedback that counts
toward a role-eligibility threshold), not just on the agent-registration side.

## Q7 — Accountability and Monitoring

Reputation Registry section: feedback is a signed value from a `clientAddress`, explicitly
excludes the agent's own owner/operator from submitting feedback about itself ("The feedback
submitter MUST NOT be the agent owner or an approved operator for `agentId`"), is revocable by
the original submitter, and is permanently retained on-chain even when revoked ("On-chain
pointers and hashes cannot be deleted, ensuring audit trail integrity"). Three actionable
patterns for Powers accountability chains governing agent roles: (1) exclude the role-holder
itself and its known operators from any `allowedRole` set that can submit accountability signals
about that role — self-reporting is not accountability; (2) allow signal *revocation* by the
original submitter (mirrors `RenounceRole`-style self-correction) without allowing signal
*deletion*, preserving the audit trail even after correction; (3) treat "permanently retained,
revoked" as different from "hidden" — revoked feedback remains visible for pattern analysis even
if it no longer counts toward an active threshold.

Validation Registry / Security Considerations: validator identity and response are both
on-chain and queryable, but "incentives and slashing related to validation are managed by the
specific validation protocol and are outside the scope of this registry" — the validation
*record* is separated from the validation *consequence*. In Powers terms: keep the mandate that
records a validation/audit result (`StatementOfIntent` or `BespokeAction_Simple` writing to an
external validation contract) separate from the mandate that acts on it
(`RevokeAccountsRoleId`/`PauseMandates`), so the consequence logic can be reviewed and reformed
via `Adopt_Mandates` independently of the recording mechanism.

## What to skip

The ERC-721/URIStorage implementation details (token minting mechanics, `agentURI` resolution
schemes, IPFS vs. base64 data-URI encoding, the exact registration-file JSON schema) are Ethereum
tooling specifics with no Powers mandate-design analogue — Powers roles are not NFTs and do not
need a portable off-chain metadata file. The specific endpoint-domain verification flow (proving
HTTPS control via a `.well-known` file) is a web-identity binding mechanism orthogonal to
governance design. The payments/x402 integration notes are explicitly out of scope of the
protocol itself and are illustrative only.

## Mandate implications

- Scale oversight (validation gates, `timelock`, staking requirements) to the value at risk of
  the specific mandate an agent role can trigger, not to organisation size or role-holder count.
- Keep an agent's base "registered/discoverable" role (open `SelfSelect`-equivalent) strictly
  separate from and weaker than any `allowedRole` grant with real governance power — discovery is
  not trust.
- For agent-triggered high-stakes mandates, require an external validation step
  (`CheckExternalActionState`/`ExternalAction_Simple` with `needFulfilled`) before execution,
  rather than relying on accumulated reputation alone — reputation is retrospective and does not
  prevent a first catastrophic action.
- Use progressive `needFulfilled` gates (soft validation unlocks a reversible preparatory
  mandate, hard validation unlocks the final irreversible one) for agent actions with a staged
  risk profile.
- Exclude a role-holder and its known operators from the `allowedRole` set of any mandate that
  records accountability signals about that same role-holder.
- Separate the mandate that *records* an audit/validation result from the mandate that *acts* on
  it, so consequence logic (thresholds, sanctions) can be reformed independently via
  `Adopt_Mandates` without touching the recording mechanism.
