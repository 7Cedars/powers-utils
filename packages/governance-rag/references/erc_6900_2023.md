# ERC-6900 (2023) — Modular Smart Contract Accounts

**Citation:** Egyed, A., Liu, F., Paik, J., Weiss, Y., Gu, H., Lim, D., Koch, R., Philipson, D.,
Ho, H., Belenkov, N., zer0dot, & Kim, D. 2023. "ERC-6900: Modular Smart Contract Accounts."
*Ethereum Improvement Proposals*, no. 6900 (Draft, created 2023-04-18).
https://eips.ethereum.org/EIPS/eip-6900.
**Analytical level:** Structural
**Most relevant design decisions:** Q1, Q4, Q6

---

## Q1 — Role Structure

Security Considerations, "Wallet/SDK Developers": a validation function installed with the
`isGlobal` flag joins a global validation pool and "can validate any of the execution functions
that expose themselves to global validation... In a sense, these global validation functions
could gain root access to the exposed native execution functions and potentially the whole
account." This is a concrete, field-tested confirmation of the existing `OpenAction` warning in
`institutionalDesign.md` ("Only assign to highly trusted roles"): the risk of a broad-scope
permission grant is not proportional to how the grant is described (a single "global validator")
but to the full set of functions it can reach once installed. Treat any Powers mandate/role
combination with `allowedRole` = PUBLIC or with an unusually wide `target`/`value` range as
requiring the same review rigor as a full admin grant, regardless of how narrow the mandate's
stated purpose sounds — scope creep happens at the boundary between "what the mandate says it's
for" and "what it is actually capable of reaching."

## Q4 — Dependency Chains

"Execution Call Flow" section: pre-execution hooks "MUST run validation-associated hooks first,
then selector-associated hooks second," and post-execution hooks "MUST be run in the reverse
order of the pre execution hooks." When multiple independently-installed checks apply to the same
call, the standard fixes a canonical, deterministic ordering rather than leaving it
implementation-defined. This is directly transferable to Powers designs that stack multiple
`needFulfilled`/`needNotFulfilled` gates or multiple accountability mandates on a single flow
position: define and document an explicit, stated precedence (e.g., "role-eligibility checks run
before content checks; the most specific veto has priority over the most general") rather than
relying on whatever order the mandates happened to be adopted in. Without an explicit ordering
rule, adding a new accountability mandate via `Adopt_Mandates` can silently change which check
"wins" when two mandates would otherwise disagree.

## Q6 — Adaptive Capacity and Reform

Security Considerations, "Module Developers": "The standard does not enforce any rules
surrounding what data needs to be installed or uninstalled when a module is added/deleted... the
`onUninstall()` function... may leave behind residual state data... This could pose security
risks... in the case where the module is reinstalled with the same entityId. The danger is that
previously set permissions or data may be unintentionally reused." This is a directly actionable
warning for Powers' reform cycle: `Revoke_Mandates` followed later by `Adopt_Mandates`
re-installing a mandate at the same position is not guaranteed to be a clean reset. If a mandate
carries associated state beyond its `Conditions` struct (e.g., accumulated vote records,
`throttleExecution` timers, or external contract state it references), that state can persist
across a revoke/re-adopt cycle and silently reactivate stale permissions or thresholds. Treat
mandate re-adoption at a previously-used flow position as requiring an explicit state-audit step,
not an assumption of a fresh start — this sharpens the existing "Critical notes" caveat on
`PauseMandates` in `institutionalDesign.md` (that restart re-adopts *original* config) into a
more general rule covering full revoke/re-adopt cycles, not just pause/restart.

## What to skip

The overwhelming majority of this document — the exact interface definitions
(`IERC6900Account`, `IERC6900Module`, `IERC6900ValidationModule`, etc.), the packed
`ModuleEntity`/`ValidationConfig`/`HookConfig` byte layouts, the manifest installation/
uninstallation procedural steps, and the ERC-4337 call-flow wiring — is Solidity interface
engineering with no governance-design analogue. It answers "how do you build a pluggable module
system for one smart contract account," which Powers already solves at the governance layer via
its own modular mandate architecture (`institutionalDesign.md` §1 "Modular mandates"); this ERC
is confirmatory of that architectural choice rather than a source of new design principles for
constitution authors.

---

## Mandate implications

- Review any mandate/role combination with a wide `allowedRole` (PUBLIC) or broad `target`/
  `value` scope with the same rigor as a full admin grant — the actual reach of a permission, not
  its stated purpose, determines its risk.
- When multiple accountability or veto mandates apply to the same flow position, document an
  explicit precedence order rather than relying on adoption order, and re-verify that ordering
  whenever a new mandate is added via `Adopt_Mandates`.
- Treat mandate re-adoption at a previously-revoked flow position as requiring an explicit
  state-audit step: confirm no stale permissions, thresholds, or external state persist from the
  prior installation before trusting the "fresh" mandate.
